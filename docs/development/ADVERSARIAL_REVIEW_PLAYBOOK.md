> 状态：Wave 2 实践沉淀，**不新增任何产品/权限/协议语义**，只约束「如何证明一条约束成立」。

## 0. 这份文档存在的理由

四个节点里，**每一次「结论错误」都不是代码写错，而是装置或口径写错**：

| 节点 | 事故 | 代价 |
|---|---|---|
| DEV-02-07/08 | 35 条攻击**全是 UPDATE 语义**，「创建轴」整类绕过从未被尝试 | 初版终审结论作废，重开一轮 |
| DEV-02-08 | `SELF_CHECK_PASS` 的种子缺一行，UPDATE 命中 0 行也返回 0 | 11 条攻击被误报为「全部绕过」 |
| DEV-02-09 | 计划里写「4 个索引」，实际总数 7（`grep -c '^CREATE INDEX'` 只数出 4 个**普通**索引，漏了 3 个 `CREATE UNIQUE INDEX`） | 立下「先跑计数命令」的规矩 |
| DEV-02-10 | 手算攻击条数（编号跳号导致），文档写 24/50，实际 17/43 | 门禁前复核抓到 4 处 |
| DEV-02-10 | 手写 BLOB id 少一位，INSERT 在攻击 SQL 第一条就被 CHECK 拒 | **8 条「拦截」全是假的** |
| DEV-02-10 | 守卫只写在 INSERT 侧，UPDATE 侧畅通 | 我自己制造的守卫自相矛盾 |
| DEV-02-10 | 「基线全拦」——通配符把新迁移一并加载，基线与加固后跑同一套 schema | 差点认定缺口是臆想的、**停止修复** |
| DEV-02-10 | 逐条向量手写注入参数，漏 4 处，语法检查通过零报错 | 那 4 条结论全部作废 |
| DEV-02-10 | 「抹掉取消者」实为 `NULL → NULL` 的 no-op，被记成绕过 | 种子行的初始值没与攻击向量成对核对 |
| DEV-02-10 | 重跑存档写成同一个文件名，后者覆盖前者 | `${f%%-*}` 对 `attack-xxx.sh` 取到 `attack`；**终审文档引用的还是更早那次全故障的存档** |
| DEV-02-10 | 装置不自声明加载了哪套 schema，直接跑得到「24 绕过」 | 汇总行形状与真结果**完全一样**，照出「0 误伤」 |

共同点：**错误的输出和正确的输出长得一模一样。** sqlite3 返回 0、grep 数到行、测试跑完退出码为 0 —— 都不告诉你「你根本没测到那件事」。

## 1. 七条铁律

### 1. 没被尝试过的攻击，不会计为失败

覆盖不了的东西不产生失败信号。**先画覆盖面矩阵，再设计向量。**

做法：跑完一轮后逐条回看攻击清单，问「哪个状态/哪个字段/哪根轴一条都没被碰到」。DEV-02-10 的 T 组就是这么来的——回看 P 组发现 `EXPIRED` 整条线、`is_human_only`、`action`/`resource_type` **三处零覆盖**，补齐后又抓到一个真绕过。

### 1-b. 装置故障最危险的形态：让基线不存在

基线「全绕过」会推着你写修复；基线「全拦」会让你**认定缺口是臆想的、停止修复**。
一个让你不再干活的错误结论，代价远大于多写一个迁移。

真实事故：`build_base` 的循环是 `00*.sql`，而新迁移 `0021_*.sql` **以 `00` 开头被通配匹配**、
case 分支里又没有对应条目 → 正式迁移被无条件加载，「只加列的影子版」形同虚设，
基线与加固后跑的是同一套 schema。

做法：

- 凡引入新迁移，**先证明基线轮与加固后轮的 schema 确实不同**；
- 证明方式是**直接断言** trigger/列的存在与否（`build_base` 后查 `sqlite_master`），
  **不是「看结果像不像」**；
- 新迁移文件名务必在 case 中显式开一条分支，别指望通配符的边界。

### 1-c. 装置必须自声明加载了哪套 schema，且断言要双向

攻击组通常靠环境变量开关控制加载哪些迁移（`INCLUDE_00xx=1`）。若脚本自己不声明、
指望调用方在命令行补齐，那么**直接跑脚本会加载出另一套 schema**，
而输出格式、汇总行、结论行**与真结果完全一样**。

实测症状：直接跑得到「24 绕过」，补齐变量得到「32 拦」—— 两者都是"合法"输出。

做法：

- 每个装置脚本自己 `export` 全部开关，**不依赖调用方记忆**；
- `build_base` 末尾加 **schema 断言**，且**双向**：
  - 期望集合由 `EXPECT_SCHEMA` **显式声明**（不是「开关为 1 就检查」——
    漏加载时条件为假、根本不会检查，等于没断言，这条是自检直接测出来的失败）；
  - 声明里有的 trigger **必须存在**；
  - **没声明的必须不存在** —— 这条防的正是 1-b 那个「基线偷偷加载正式迁移」的事故。
- **断言写完要配自检脚本**，覆盖「全加载 / 漏一个 / 多加载」各类组合，
  证明它真的会拦。自检脚本本身也要被自检：本次自检直接测出两处设计缺陷
  （漏加载时条件为假、逗号分隔却按空格循环），当场修正。

### 2. 装置故障有三种伪装形态，必须分别识别

| 形态 | 表现 | DEV-02-10 实例 |
|---|---|---|
| 把**失败**伪装成**通过** | 装置没跑起来，却输出了「合法路径未误伤」 | seed 报错伪装成结论 |
| 把**没测到**伪装成**测到了** | 攻击第一步就失败，输出与真拦截完全同形 | id 少一位 → 8 条假拦截 |
| 把 **no-op** 伪装成**绕过** | SQL 返回 0，但实际改了 0 个值 | `is_human_only` 改 0 而种子就是 0；「抹掉取消者」而该列种子值本就是 NULL |

第三种最隐蔽：**判据必须是「造成了规格禁止的危害」，不是「SQL 返回了 0」。**

### 3. 被测数据的**任何**构造路径都必须在种子自检覆盖范围内

写在攻击脚本里的 `INSERT`/`CREATE` 一律视为**未经验证的装置状态**。绕过自检的攻击，其后续拦截结论不成立。

做法：所有攻击起点行进 `seed.sql`，`build_base` 做逐表计数断言，行数不对直接判装置故障并**不产出任何结论**。

### 4. 跨 INSERT/UPDATE 的约束必须双侧落地，各配一条向量

只在一侧写死等于没写——而且比没写更糟：它让人以为该面已封。

做法：任何「X 不得携带 Y」类约束，INSERT 侧和 UPDATE 侧都要写，且**各配一条对照向量**，把「两侧一致」变成可复验结论而不是口头声明。

### 5. 每个新约束问一句：「这句是规格写的，还是我想要的？」

后者降级为文档登记，不进 trigger。追问链要写进迁移文件注释，例：

> §7 把「decider 与 requester 不构成自批」列为迁移前置条件 → `0009` 的 CHECK 靠 `decided_by_human_id` 的**值**执行该禁令 → 该列一旦可事后改写，CHECK 立即失效 → 决定人是迁移的**执行事实**，不是可订正的备注。

注意反向操作同样适用：**发现自己在某处加严了规格，也要撤掉**。DEV-02-10 移除 `decision_notes` 限制即属此类。

### 6. 能脚本计数的量，写文档前先跑计数命令

这条已经被立过两次、也违反过两次。**编号跳号（T-13 → T-16）本身就是危险信号**——它让「编号范围」与「实际条数」脱钩，口算必错。

做法：计数取自**两个独立来源**（定义处 + 输出文件）交叉验证，不采信任何单一来源，不采信口算。

**还要核「你数的是不是你要的那个数」。** DEV-02-09 那次 `grep -c '^CREATE INDEX'` 得 4，数字本身没错——错的是把「4 个**普通**索引」当成了「总索引数」，实际还有 3 个 `CREATE UNIQUE INDEX` 不匹配该正则。**grep 的模式本身就是一次口径选择。**

### 7. 规则要下沉为代码，不能只写进文档

写进审计文档的规矩，下一个节点一定会有人（包括我自己）绕过。**凡是「判定正确性」依赖人不出错的环节，都要改成靠机制。**

实例：`lib.sh` 的 `hex32()` 作为所有被测 BLOB id 的唯一出口，位数或字符非法即返回非 0，脚本当场 `exit 2`。

配套技巧：**让装置闭嘴比让它报错更重要**。子 shell 里的计数器传不回父 shell，与其留一条半可信的 ERROR 行，不如**不输出**——没有输出就没有可被误读的结论。

## 2. 新建攻击装置的自检清单

装置上线前逐条打勾，缺一条就不许产出结论：

- [ ] 种子有**逐表计数断言**，且每次改种子同步更新期望值
- [ ] 种子自身跑在带 `PRAGMA foreign_keys=ON` 的连接里（连接级设置，每次都要开）
- [ ] 多语句攻击用 `.bail on` 包住（否则第二条失败时 sqlite3 仍返回 0）
- [ ] 所有被测 BLOB id 经过唯一出口校验，无手写字面量
- [ ] 攻击起点行全部在种子里，脚本内无现造的被测数据
- [ ] 每条向量**改了确实不同的值**（对照种子值检查，排除 no-op）
- [ ] 装置故障时**明确区分**「装置坏了」与「攻击成功」，且故障态不计入任何统计
- [ ] 对照组不是「攻击的反面」，而是**规格明确允许的路径**
- [ ] **基线轮的 schema 与加固后确实不同**，且用直接断言证明（不是看结果像不像）
- [ ] 种子行的初始值与每条攻击向量**成对核对**：攻击要写的值必须与种子值不同
- [ ] 共享装置（`lib.sh`/seed）变更后，**所有调用方都已重跑**，无一报装置故障
- [ ] **装置脚本自声明全部加载开关**，不依赖调用方在命令行补环境变量
- [ ] `build_base` 有 **schema 双向断言**（有的必须存在、没有的必须不存在），且有自检脚本覆盖
- [ ] 每次重跑的存档**文件名互不覆盖**，且文档引用的正是本次那份（不是更早的旧存档）

## 3. 门禁前的机械化数字复核

这是拦住 DEV-02-10 那 4 处数字错误的唯一动作。它不是仪式，是流程里的固定一步。

做法：对即将定稿的文档，把其中每一个「N 条 / N 个 / N 行 / N trigger」逐个跑出对应计数命令：

```
grep -c '^run_attack' attack-xxx.sh          # 定义处
grep -c 'BLOCKED'   results-xxx.txt          # 输出处
```

两个来源对不上就**不许写进文档**。同理，新建/修改迁移后必须重算：文件行数、trigger 数、索引数、CHECK 数。
