## 2. 主依据是 `TECH_STACK_AND_STANDARDS.md` §5，前五个节点都没用过它

> - Task 领取在同一事务中校验状态、依赖、Binding、权限、并发上限并创建 lease/fencing token。
> - **心跳只能延长匹配当前 token 的租约；接管/超时生成新 token，旧执行者所有写入返回 `RUN_FENCED`。**

配合 `DATA_CONVENTIONS.md` §2：

> `fencing_token`｜每 Task 执行世代单调递增整数｜**不能使用随机 Session ID 替代**

「单调递增」是判定式的基础：**旧 token 必然 `<` 当前 token**。

## 3. 「双主 Run」的漏洞在执行层，不在记录层

`adapter-supervisor` 校验每条通知的 `fencing_token`——但比的是
**它启动时被配置进去的那个**：

```text
crates/adapter-supervisor/src/protocol.rs:1089 → pub fn new(expected_context: RunContext) -> Self {
crates/adapter-supervisor/src/protocol.rs:1223 → if fencing_token != self.expected_context.fencing_token {
```

它**再也不从数据库重读当前世代**。于是这个序列通过它的全部检查：

    t0  Run A 领取 Task T，token = 7；supervisor_A 以 expected = 7 启动
    t1  A 卡住；§3 生成新 token = 8；Run B 领取 T；supervisor_A 仍在跑
    t2  A 醒来上报心跳：presented 7 == expected 7 → 被接受

**`0012` 的守卫挡不住这个**：它检查「一个 Task 不得同时有两个活动 Run **记录**」，
而 `t2` 时刻 A 已被 fence 成终态，记录层确实只有一个活动 Run。
**`0012` 停住了重复的记录，停不住那条记录曾经所属的进程。**

所以本节点的核心要求就是一句话：**判定必须对着当前世代比，不能对着启动时的快照比。**

## 4. 世代比较，绝不用 `!=`

单调性让三种情况可区分，而它们不是同一个问题：

| presented vs current | 含义 | 判定 |
|---|---|---|
| `<` | 上一任执行者，接管或超时后的常态 | `RUN_FENCED` |
| `==` | 当前执行者 | 放行，另看租约窗口 |
| `>` | §2 单调性下不可能 = 数据故障 | `RUN_FENCED`，但**绝不描述为接管** |

`!=` 会把第一行和第三行压成一个布尔。执行者出示**未来的** token，
意味着世代分配器或调用方的读取有问题，**那和例行接管需要不同的信号**。

## 5. `RUN_FENCED` 与 `RUN_LEASE_EXPIRED` 是两码

§5 的 `RUN_FENCED` 讲的是**身份**（「旧执行者」）；
`RUN_LEASE_EXPIRED` 讲的是**时间窗**（目录 details 给 `expired_at`，
补救动作是「新 Run」）。

持有当前 token 但租约已过期的执行者**仍然身份有效**，
但它的心跳**不能复活租约**——否则租约永不过期，
§3 的 `RUNNING → TIMED_OUT` 对活进程就不可达。

| 情形 | 判定 | 码 |
|---|---|---|
| 旧 token，租约未过期 | `Refused` | `RUN_FENCED` |
| 旧 token，租约已过期 | `Refused` | `RUN_FENCED`（**身份优先**，不是 `Expired`） |
| 当前 token，租约未过期 | `Renewed` | — |
| 当前 token，租约已过期 | `LeaseExpired` | 窗口关了，但**没被 fence** |

把最后一格报成 `RUN_FENCED`，正是拆两码要避免的**误诊**——
它会把调用者指向一次从未发生的接管。

## 6. `RUN_LEASE_EXPIRED` **不**加入 `RunErrorCode`（裁决记录）

目录里有这个码（`ERROR_CATALOG.md:87`，`retryable=否`），
但 `RunErrorCode` 的 9 个变体里没有它，**本节点也不加**。

**理由**：DEV-03-06 立的测试 `every_code_the_run_machine_can_raise_is_enumerated`
要求 `RunErrorCode::ALL` 里的每个码都能被 `RUN_EDGES` 或 `CREATE_QUEUED` 产生，
**而 §3 没有任何行产生租约过期码**。加进去会打破那条不变式。

所以按 `INTERNAL_UNEXPECTED` 在 `run_retry` 里的先例，
它作为 `LeaseRefusal::Expired` 这个独立形状携带冻结线名。
`LeaseRefusal::as_run_error_code()` 对它返回 `None`——
**诚实的答案，而不是找一个凑数的映射**。

**净效果**：DEV-02-11 与 DEV-03-06 的冻结结构零改动。

## 8. 三处刻意的不建模

**`decide_write` 不收 `LeaseSnapshot`。** §5 把写入准入限定在「旧执行者」——
那是**身份**问题。租约窗口是另一个问题、另一个码，由 `decide_renewal` 回答，
规格从未说「窗口关闭就拒绝写入」。收下这个参数却不基于它分支，
会让签名**暗示一个规格没有的耦合**，而读签名的人会理所当然以为过期已被考虑。

**「输出」不是 §3 迁移，但也不是凭空造的。** `输出` 在 `docs/specs/` 里出现 **3 次**：

| 位置 | 是什么 |
|---|---|
| `ERROR_CATALOG.md:93` | `RUN_OUTPUT_TOO_LARGE`——产物大小，**不是**写入种类 |
| `adapter/v0/PROTOCOL.md:154` | 「禁止输出 token、cookie」——动词义，**无关** |
| `adapter/v0/PROTOCOL.md:174` | 「初始化、健康、启动、状态、**心跳、输出**、取消、对账、**完成**、失败……」——协议事件种类 |

最后一条是**正向支持**：协议把 `输出` 与 `心跳`、`完成` 并列成一类事件。
`docs/development/QUALITY_GATES.md:207`（并发 Run 预算）同样写着「同时**心跳、输出**和取消」。

所以把它建模成一种**写入种类**，来源是节点标准「旧 token 的心跳、输出和完成都被拒」
**加上**上面两处把输出与心跳并列的规格语境，**仍然不是 §3 的迁移表**——
§3 至今没有这一行，故已标为 **derived reading**。

> 上一版此节写的是「`输出` 在规格里只出现两次，都不是本节点语境」。
> 计数错（3 次），方向也错：漏掉了 `PROTOCOL.md:174`——
> 而那一条恰恰**支持**建模，是本节最强的正面依据，不是免责声明。

**heartbeat deadline 不新建列。** §3 说 `STARTING → RUNNING` 要「设置 heartbeat deadline」，
`UNKNOWN → RUNNING` 要「恢复 heartbeat deadline」，而 `0001`～`0022`
**没有任何一列叫 heartbeat**（`grep -rniE "heartbeat" migrations/` 无输出）。
本节点按**派生量**处理（= `leases.expires_at`），理由是 §5 说
「心跳延长的是**租约**」；若 deadline 是独立列，那句话该说「延长 deadline」。
**这是倾向不是结论，已登记待裁决。**

### 10.1 Q-13 的 C2 曾有一个静默绕过（已修，且我第一次只修了一半）

独立审查指出：把两条 in-repo 引用**移出 ```` ```text ```` 围栏**、行号与引文一并编造，
装置报 `checked … 0 in-repo citations, 0 not verified` 并 **PASS**。
**实测复现，审查成立。**

根因不是「围栏匹配写错了」——裸围栏本来就该放示意图、不该被查。
根因是**「不在检查范围内」被当成了「不存在」**：
装置停止检查时，输出的形状和「全部通过」**完全一样**。

第一次修法是新增 **C3**：任何**形状像引用**的行，若落在被检查的围栏之外，一律报 FAIL。
我当时的说法是「**C3 认的是行的形状，不是某个具体手法**」。

**第二次独立审查证伪了这句。** C3 的归一化只剥三种前缀
（空白 / `///` / `//!`），所以引用只要带上任何别的装饰（`` ` ``、`* `、`> `、`- `）
就整个隐形，装置照样报 `0 citation-shaped lines out of scope`。
更要命的是**直接删掉两条引用**：C3 看不见一条不存在的行，
输出是 `0 in-repo citations, 0 not verified` / **PASS**——
**原来的失败原封不动地又回来了一次，而 C3 就站在它旁边。**

两处都补上：

- **归一化放宽**为 `strip_decoration`（`^[\s/*>`'"=~+\-–—.:|!]+`）。宁可多剥一点——
  剥多了最多让 C1 去跟冻结规格对质，剥少了引用就彻底隐形。
- **新增 C4 引用数下限** `EXPECTED_CITATIONS`。**探测器抓不到「没有」，只有下限能。**

| evasion | 修前 | 只加 C3 | 加 C3 + C4 |
|---|---|---|---|
| 移出围栏 + 编造行号 | PASS | C3 FAIL | C3 FAIL |
| ```` ```text ```` 加尾随空格 | PASS | C3 FAIL | C3 FAIL |
| 围栏外 + 前导 `* ` | PASS | **PASS**（C3 看不见） | C3 FAIL |
| 围栏外 + 前导 `` ` `` | PASS | **PASS** | C3 FAIL |
| 围栏外 + 前导 `// ` | PASS | **PASS** | C3 FAIL |
| **直接删掉两条引用** | PASS | **PASS**（行不存在了） | **C4 FAIL** |

六种全部 `exit=1`。修后真实现状 `0 citation-shaped lines out of scope` / `PASS`，
`--inject-bad` 仍 `exit=1`，q12 不受影响（`exit=0`）。

**C3 是探测器，不是保证。** 我第一次把它当成了保证——
「认形状不认手法」这句话听起来像是设计上的稳健，实际只是一个更窄的正则。
**探测器只能对「还在那儿的东西」负责；「东西没了」只有断言能管。**

它的三条设计约束（都是被自己的错误逼出来的）：

1. **每行写明期望判定，不符即 `exit=1` 并指名行。** 手写 shell 矩阵
   把「改名 `..._v2`」那行**报成了绿**（单跑是红的）；一个会误报的矩阵
   比没有矩阵更糟，因为它冒充证据。
2. **三个判定不是两个**：`green`／`red`／**`broken`**（没跑出结果行）。
   让 `0012` 解析失败的变异会让所有用例报错——朴素问法会把这当成「抓住了」。
3. **`--preflight` 先确认每行变异后的 schema 真能建起来。**
   **这一项当场抓出两行测错了东西**：只注释掉 `CREATE TRIGGER` 那一行，
   留下悬空的 `BEFORE UPDATE ON …`，文件不再是 SQL；它们红是**语法错误**的红，
   不是守卫被删的红。**测的不是它声称测的东西，红得再准也不算数。**

现状：**47 行**（40 条必须红、6 条必须绿，另有 L00 基线绿），正式跑 `PASS`，
`--expect-fail` 自证 `exit=1`。**打的是 `cargo test -p persistence-sqlite` 整包，
不是单个测试二进制**——见 §13.6。
详见 §13.3～§13.7。

**本节点装置学到的三件事，都写在装置自己的 docstring 里**：
「只做删除」是盲区（弱化类要另写）、「按名字装上了」不等于「会说话」
（`RAISE(IGNORE)` 让守卫沉默而 `sqlite_master` 无感）、
**测得比测试套件还小的矩阵会把「归档在别处」误判成缺口**。

**第十一次审查给这三条加了第四条：同一个 trigger 的不同变异形状，覆盖程度可以差到零。**
`reviews_consistency_update` 此前**只有一行 L09**（整条删除），
而整条删除恰好是全套件唯一看得见的形状——名字没了，存在性检查就红。
换成 `RAISE(IGNORE)`，trigger 仍以原名装着，**那一行覆盖不到**。
**矩阵里某条规则出现过，不等于它被覆盖过。** 见 §13.7。
**补的不只是一个 trigger，是这个形状。** 11 个 trigger 里当时只有 6 个有

没有一行问过「这里到底有没有在拒绝」**。已补 L42～L46，并给装置加了
`shape_coverage()` 结构断言：它从迁移里读 trigger 名、从装置里读 `neuter(t, "…")`
目标，**对不上就 `exit=1`**。这样缺口由**形状**关掉，而不是一次关一个实例。

**「只做删除」是这一节最贵的一条教训。** 前 24 行全部是删除类变异，
而删除是**最容易被发现**的一类；弱化（`=` 改 `>=`）守卫还在、还在拒绝东西，
只验删除的套件**全绿通过**。第九次审查的四条阻断面里有三条正是弱化或删除落在
其余九个 trigger 上——它们此前**一行覆盖都没有**。**装置只对它会做的那一类变异负责。**

**一条实测过的上界**：`preflight` 用系统 `sqlite3` 施加迁移，

##### 更正（第十一次审查后）：`RAISE(IGNORE)` 是 fail-silent，不是「不变量被破坏」

这一节的措辞需要往下压一格，压的依据是**实测**，不是推理。
原写法把 B1/B2 说成「真洞 / 不变量被破坏」。**这不准确。**

在 pristine 与 `RAISE(IGNORE)` 两种库上跑同一条越权语句
（`UPDATE reviews SET team_id = <另一个 Team>`）：

| 库 | 调用方看到 | `rowcount` | 该行是否真被改 |
|---|---|---|---|
| pristine | `Err: Review consistency violation` | — | 否 |
| `RAISE(IGNORE)` | **`Ok`** | **0** | **否** |

也就是说：**存储层的不变量并没有被破坏，行还是原来那一行。
坏掉的是「写入是否生效」这件事的信号**——
BEFORE trigger 里的 `RAISE(IGNORE)` 会丢弃这次写入、放弃同一行后续的触发器程序，
然后**把成功返回给调用方**。

正确的定性是 **fail-silent（静默丢写，调用方误以为成功）**，
不是完整性被破坏。这个区别不是文字游戏：

- 说「不变量被破坏」→ 暗示库里已经脏了，要去查数据、可能要回滚；
- 说 fail-silent → **库是干净的，脏的是调用方的认知**。
  取而代之的风险是**静默丢更新**（用户改了评论、以为存上了，其实没有）。

B1/B2 的测试覆盖**依然有效且必须保留**——它们断言 `is_err`，
在 `RAISE(IGNORE)` 下确实转红。**要改的只是定性，不是测试。**

**B4 也不是子句问题**：trigger 对某类列**不再触发**。
按子句穷举永远看不到它，只能按**列清单**测。

#### 阻断面：`reviews_consistency_update` 从来没有测过，矩阵也从来没碰过它

> 我的探测脚本自己也出过一次错，先记下来：`sql_for` 用 `label.startswith("version")`

> 差点据此得出「这条守卫过度拒绝」的错误结论。**先判因再下结论。**

**为什么前十轮没抓到。** 因为这个 trigger 在矩阵里**只有一行 L09**，

`sqlite_master` 里的名字没了，存在性检查就红。

换句话说：**同一个 trigger 的两种变异，一种被覆盖，一种完全没有。**

更该记的是它和 `reviews_consistency_insert` 的关系：

**「兄弟守卫有测试」不等于「这条也有测试」，迁移里重复写两遍的谓词要按两遍算。**

#### 补的是形状，不是这一个实例

修完 L41 之后，问了本轮该问而前十一轮都没问的一句：
**`0012` 十一个 trigger 里，有几个被 `RAISE(IGNORE)` 问过？**

| | trigger 数 |
|---|---|
| 有 `neuter` 行 | **6** |
| 只有子句行 / 删除行 | **5** |

那 5 个（`leases_consistency_insert/update`、`reviews_consistency_insert`、
`runs_consistency_insert/update`）**每一行都在问子句**，
**没有一行问过「这个守卫到底还拒不拒绝」**。
这不是覆盖率不足的措辞问题，是**问题本身没被问过**：
一个只会触发、什么都不说的 trigger，可以把全部子句行都读成 `red`。

补 **L42～L46**，并给装置加了一条**结构断言** `shape_coverage()`：
从迁移里读 trigger 名，从装置里读 `neuter(t, "…")` 的目标，**对不上就 `exit=1`**。

```
11 个 trigger，11 个有 RAISE(IGNORE) 行      → PASS
删掉 L46 的副本                              → exit=1，并指名 runs_consistency_update
```

**为什么要断言而不只是补五行**：前三次同类缺口（弱化类、其余九个 trigger、
本次）**每一次都是被独立审查发现的**，也就是每一次都要付一整轮审查的代价。
**断言把「下一次」的成本从一轮审查降到一次 grep。**

**这个新测试自己过了它的矩阵**（第十轮那条规则的第二次应用）：
`--only L41` → `expected red / got red`；
`--only L41 --expect-fail` → `SELFTEST_EXIT=1`；
`--only L00` → `CONTROL_EXIT=0`。

`RAISE(IGNORE)` 是「拒得不够」，**「全拒」是它的镜像**，
两种都该被同一批测试挡住。
