## 1. 目标

让 Claude Code、Codex（以及配置了 MiniMax 等模型的同类工具）以固定岗位组成 AI 开发团队。你主要和 Leader 对话；Teamspace 负责建任务、派工、隔离执行、回收结果和留痕，你不再是在各个 AI 之间搬运任务和上下文的人。

四条原则：

1. **可用优先**：每个里程碑结束时，你都能用它完成一件真实的事，而不只是完成「底座」。
2. **纵向切片**：一次打通「界面 → 后端 → 真实 AI 执行」，再逐步加厚。
3. **用中迭代**：M3 完成后就用 Teamspace 开发 Teamspace，下一步做什么由使用中的问题决定。
4. **够用就好**：规则写在 Rust 代码和测试里，不预先冻结成规格；用不到的能力不提前实现。

## 3. 新架构

```text
┌───────────────── Tauri 桌面应用 ─────────────────┐
│  React 界面（按 Figma 画板实现）                   │
│        ↕ Tauri IPC：命令调用 + 事件推送            │
│  teamspace-core（Rust 库）                         │
│    store    SQLite：单一 schema，只保留必要约束     │
│    service  团队 / 岗位 / 任务 / 执行 / 验收用例    │
│    runner   派工队列、并发上限、取消、重启恢复      │
│    harness  Claude Code / Codex / Mock 驱动         │
│    git      worktree、分支、diff、合并              │
└──────────────────────────────────────────────────┘
          ↑ 同一个 SQLite 文件
  teamspace-mcp（M4，stdio MCP 服务）← Leader（Claude Code / Codex）
```

关键做法：

- **Harness 实例 = CLI 类型 + 配置档案**。例如「Claude Code（默认）」「Claude Code（MiniMax 模型）」「Codex」。平台只记录 CLI 路径、模型名和配置文件路径，不保存任何密钥，登录由 CLI 自己管理。
- **执行**：每个 Run 新建 git worktree 和分支，生成任务说明，以非交互方式启动 CLI（`claude -p --output-format stream-json`、`codex exec --json`），实时解析输出并推送到界面。结束后收集摘要、改动文件和提交，任务进入待验收。
- **验收**：查看摘要和 diff。通过后由你确认合并到基线分支；退回时附上意见，在同一 worktree 续接会话重新执行。
- **一致性**：同一任务同时只能有一个活动 Run（数据库唯一索引）；Run 写入结果前检查自己仍是当前 Run；应用重启时，把没有对应进程的「运行中」Run 标记为「已中断」。
- **数据位置**：数据库和 worktree 放在 `~/Library/Application Support/` 下的应用目录，不写入你的仓库。

## 4. 里程碑

「可用标志」写的是该里程碑结束时你能用它做成的事。

### M1 团队与任务

- 应用框架：左侧导航、团队切换、页面路由，按设计 Token 还原视觉。
- 创建团队与工作空间：选择本地 Git 仓库作为工作空间。
- 岗位：Leader / 产品 / 前端 / 后端 / QA 模板，可增删改；每个岗位有职责说明和工作约定。
- Harness：自动检测本机的 Claude Code 和 Codex，显示版本和可用状态；创建 Harness 实例（含配置档案）；把岗位绑定到 Harness。
- 任务：看板（TODO / READY / DOING / REVIEW / DONE / BLOCKED，CANCELLED 默认收起）、创建与编辑表单（标题、说明、文件引用、负责岗位、依赖）、任务详情。
- 活动记录：所有变更写入事件表。

**可用标志**：把一个真实仓库建成团队，配好岗位和 Harness，把待办拆成任务放到看板上。

### M2 派工执行（基于 ACP，D13）

- Harness 实例 = ACP Agent：启动命令、参数、环境配置档案；内置预设：Claude Code（claude-code-acp 适配器）、Codex（codex-acp 适配器）、MiniMax Code（`mcode acp`）、Gemini CLI，也可自定义任意 ACP Agent。
- 在任务详情点「开始执行」：建立隔离的执行目录（Git 仓库用 worktree；普通文件夹的隔离方式在 M2 规划时与你确认），通过 ACP 创建会话并发送任务说明（岗位说明、工作日志、任务与引用文件），实时显示进度（消息、工具调用、文件改动、计划），结束时显示成功、失败或已取消。
- 权限：Harness 的权限请求按岗位权限自动批准或拒绝，超出范围的转给你确认。
- 异步与恢复：会话可取消、可续接；应用重启后可恢复或标记为已中断。
- 执行摘要自动写入岗位工作日志。
- Mock Agent：用于测试和演示，不消耗额度。
- 扩充 ACP 预设：CodeBuddy（`codebuddy --acp`，本机已握手通过）、Qoder CLI（`qodercli --acp`）、Grok Build（`grok agent stdio`，需 SuperGrok Heavy 订阅）、Qwen Code、Kimi CLI、OpenCode。每个新预设至少完成一次真实握手后才加入；本机未安装的先由你决定是否安装。Antigravity（agy）与智谱 ZCode 暂无官方 ACP 支持，暂不加入。调研结果见 2026-10-13 对话记录与 ACP 官网 Agent 列表。

**可用标志**：把任务派给 Claude Code 或 MiniMax，看着它工作、批准它的权限请求，结束后拿到结果，岗位日志里留下记录。

### M3 验收闭环（v0.1，可日常使用）

- 验收页：执行摘要、改动文件列表、逐文件 diff。通过后合并到基线分支，有冲突时提示并转为人工处理；退回时填写意见，续接会话重新执行。
- 依赖：前置任务完成后，下游任务自动变为 READY；创建循环依赖时拒绝并指出环路。
- 文件：浏览工作区里的 Markdown，任务和文件可以双向跳转。
- 活动与审计：按任务、岗位、时间筛选。

**可用标志**：完整走通「建任务 → 派给 AI → 验收 → 合并」，开始用 Teamspace 开发 Teamspace。

### M4 Leader 编排（v0.2，V2 核心体验）

- `teamspace-mcp`：提供给 Leader 的工具，包括查看团队、岗位和 Harness，创建、分配任务和设置依赖，查询状态和结果，发起和完成验收，给岗位发消息。
- 一键接入：为 Claude Code / Codex 生成 MCP 配置。
- 对话入口（你于 2026-10-13 确定）：你在 Leader 自己的终端里对话（例如在工作空间目录打开 Claude Code），Teamspace 只提供 MCP 工具箱，不做应用内对话面板。
- 权限边界：Leader 可以创建、派发、查询和验收普通任务；换绑、修改权限、合并到主分支等操作只能由你执行。

**可用标志**：你只在 Claude Code（Leader）里说「把登录模块拆成前后端，让 Codex 做后端」，任务就会出现在看板上并开始执行，完成后 Leader 能查到结果。

### M5 岗位通信与待我处理

- 岗位消息：Leader 与岗位之间、岗位与岗位之间的消息都经 Teamspace 中转、持久化，并关联任务。投递方式是让目标岗位的 Harness 处理消息，再把回复传回来。
- 待我处理：验收、失败、阻塞和需要你拍板的决策集中在一处处理。
- 应用内通知：状态变更提醒。

### M6 换绑与上下文继承

- 更换 Harness 的三种方式：当前执行完成后再换；取消并在新 Harness 上重跑；人工接管。
- 岗位启动包：新 Harness 接手时，自动带上岗位说明、未完成任务、近期结果和相关文件。

### M7 打磨与发布

- 窄屏、键盘操作、无障碍。
- 性能：1 万条任务和事件时常用页面依然流畅。
- 本地打包 `.dmg`（未签名，自用）、数据备份与导出。

## 6. 暂不做

- 自动拆解任务、按能力或成本自动调度、自动部署。
- 多人协作、云端控制面、邮件或即时通讯等外部通知渠道。
- 复杂的权限策略语言、全量审计导出。
- 代码签名、公证和对外发布。

## 7. 工作方式

- **文档**：本文件是唯一的进度来源；`docs/DECISIONS.md` 记录关键决策，每条几行。不再写审查报告、任务包和证据目录。
- **质量底线**：`pnpm run check` 通过（格式、lint、类型检查、测试）。核心逻辑必须有自动化测试：状态流转、git 操作、Harness 输出解析，以及用 Mock Harness 跑通的执行全流程。
- **节奏**：每完成一个功能就提交；每个里程碑结束时演示给你，你实际用过之后的反馈进入下一轮。
- **安全底线**：不提交密钥；没有你的明确同意，不推送、不发布、不产生费用、不操作生产数据。

## 8. 开发团队

一个 Team 不由一个执行者替代。总指挥负责拆任务、写任务说明、派工、审查、合并和集成验证，原则上不直接写业务代码；实现交给按工作强度选配模型的执行者。Claude 账号额度有限，约一半功能开发交给 MiniMax M3.1。

| 岗位 | 执行者 | 适用工作 |
|---|---|---|
| Leader / 总指挥 | Claude 主会话（Opus） | 拆解与派工、任务说明、审查与合并、集成验收、与你沟通 |
| 架构 / 内核 | 子 agent · Claude Opus | 接口契约、核心业务规则、一致性相关代码 |
| 功能开发 A | 子 agent · Claude Sonnet | 其他任务依赖的地基（前端骨架、命令层）和最复杂的页面 |
| 功能开发 B | MiniMax Code CLI · M3.1 | 按契约实现功能、按 Figma 截图还原页面（原生多模态）、交叉审查 |
| 工程杂务 | 子 agent · Claude Haiku | 依赖与配置、文档同步、批量机械修改 |

执行方式：

- Claude 子 agent 通过 `.claude/agents/` 里的岗位定义启动：`team-kernel`（Opus）、`team-dev`（Sonnet）、`team-chore`（Haiku），定义里写明完整模型 ID。
- MiniMax 任务用 `mcode exec` 在独立 git worktree 中运行，Figma 截图和设计稿代码作为附件提供；交叉审查用 `mcode exec review`。M3.1 写的代码由总指挥审查后再合并。
- Codex 不参与（账号即将到期）。M3 例外：Codex CLI（GPT-6.1 Sol）在账号到期前约 3 天临时加入，承担边界清晰的内核任务和交叉审查（`codex exec -C <worktree> -m <模型> --sandbox workspace-write --json -o <结果文件>`；审查用 `codex exec review`），见第 15 节。

协作规则：

- 每个任务的说明写清目标、输入（文件、Figma 节点）、允许修改的范围和完成标准。
- 并行任务各自在独立的 git worktree 中工作并提交；总指挥审查 diff、运行 `pnpm run check` 后合并到工作分支。
- 新依赖在工程准备任务中一次加齐，后续任务不改依赖和锁文件，减少合并冲突。
- 执行者不推送、不修改 `archive/` 和 `sources/`、不调用真实 Harness。
